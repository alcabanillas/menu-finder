## Context

See `proposal.md` for the motivation. What exists and constrains the approach (read from the code, 2026-10-04):

- **`infrastructure/auth/create-account.ts`** exports `createAccountCreator(config)`, which returns `(account) => Promise<Result<{ userId }, AccountError>>`. It builds the open-sign-up instance (MF-20.1 D1, option c), checks the email before any query, asks first whether the email is taken, and maps the library's error codes to `AccountError` (`invalid-input` with the field, `email-taken`, `failed`). Its tests cover those cases and the hostile values.
- **Boundary:** only `src/composition/cli-container.ts` may import it (`account-creation-boundary.test.ts` lints three files). `application/` cannot import `infrastructure/`, so the use case needs a port.
- **CLI:** `src/cli/run-cli.ts` dispatches `migrate|recipes|menu|embed` and rejects any extra argument; `src/cli/index.ts` is the only file that touches `process`; each command is `run<Name>({ <container function>, print })` returning an exit code, with `requiring(env, names, work)` and `withPool` in the container (`cli-container.ts`).
- **Existing ports read for this design** (`src/application/ports/`): `DocumentSource`, `EmbeddingsPort`, `MenuRepository`, `RecipeRepository`, `RecipeEmbeddingRepository`, `MigrationRunner`, `RepositoryError`. None covers identity or accounts.
- **Library:** `better-auth` 1.7.6. With sign-up closed there is no public server call that changes a password; `internalAdapter.updatePassword` exists but is an internal surface (the same trade-off as D1 option b).

## Goals / Non-Goals

**Goals:**
- A command that makes the account of MF-20.1 reachable by the author, with the password handled safely.
- The port and use case that MF-20.1 D3 deferred, with the existing function as their adapter, so MF-20.3 changes nothing here.

**Non-Goals:**
- Changing or resetting a password, deleting an account, listing accounts (new roadmap item for the first; the others have no need yet).
- The web side of the session (MF-20.3) and rate limits (MF-21).
- Any account data beyond email, name and password.

## Decisions

Status: D1 to D5 are **decided by the author on 2026-10-04**: D1 in the chat, D2, D3 and D5 by approving the plan, D3 (optional name) and D4 (fixed base URL, with a comment in the code) one by one. Nothing is copied to `context/decisiones.md` before the closing task.

### D1. How the command receives the password

**Decided by the author (2026-10-04).** A no-echo prompt when stdin is a terminal, one line of stdin otherwise. Never an argument, never an environment variable.

| Option | For | Against |
|---|---|---|
| No-echo prompt | Leaves nothing in the shell history, `ps` or a file | Not scriptable |
| Prompt, with stdin when there is no terminal | Covers the manual use and the demo account (`echo ... \| pnpm ingest account ...`) | A little more code |
| Generated by the command | Strong and never typed | Printed once; has to be stored right away |
| Environment variable | Simplest | Stays in the environment or in `.env.local` |

Chosen: the second. The author runs it alone and locally, so the prompt is the usual case and stdin covers the demo account without leaving the password in a file. Reading lives in `src/cli/index.ts` (the only file that touches `process`) and is injected into the command as `readPassword: () => Promise<string>`, so the command is tested with a fake.

### D2. A new port, `AccountCreator`

MF-20.1 D3 left the port for this change. `src/application/ports/account-creator.ts`:

```ts
interface AccountCreator { create(account: NewAccount): Promise<Result<{ userId: string }, AccountError>> }
```

`NewAccount` and `AccountError` move from `infrastructure/auth/create-account.ts` to the port file (the application layer owns the types of its ports, as `MigrationError` does). The existing function stays and becomes `AuthAccountCreator implements AccountCreator`; its tests keep passing with the types imported from the port. Why no existing port fits: the six ports read in Context move menus, recipes, embeddings, documents and migrations; none holds identity. Named by domain concept (`account`), not by the library.

Alternative: the command calls the infrastructure function through the container with no port. Rejected: `cli/` cannot import `infrastructure/`, and the use case would have nothing to depend on.

### D3. The use case does almost nothing, on purpose

`createAccount({ accounts }, input)` in `src/application/use-cases/create-account.ts` applies three rules that are not the library's: the display name defaults to the part of the email before the `@` (a blank name counts as none), an empty password is refused with `password-required` before the port is called, and a failure reason that repeats the password has it replaced by `[hidden]`. The last two came up while implementing (the spec already requires "no password given" and "a failing creation does not print the password"); the password reading itself is `src/cli/read-password.ts`, with its own tests, because it is the only code that touches the terminal. Everything else (email limits, password limits, repeated email) stays in the adapter, already tested there. Putting those checks in the use case too would duplicate them in two layers.

Alternative: no use case, the command calls the port. Rejected: the default name is a rule of the application, and `cli/` commands in this project call use cases, not ports.

### D4. Wiring in the CLI composition root

`createCliContainer(env).createAccount(input)` uses `requiring(env, ['DATABASE_URL_UNPOOLED', 'BETTER_AUTH_SECRET'], …)` and `withPool`, like `migrate`. The library needs a base URL to be built; the CLI never serves a request, so the container passes the fixed URL `http://localhost:3000` (the one the MF-20.1 tests use) and no new variable is required. The constant carries a comment saying why: the library only uses the base URL to build email-verification links, the system does not verify emails (SEG-sistema-cerrado), and the session cookie is signed with the secret, not the URL, so an account created here signs in on the deployed web. Alternative: require `BETTER_AUTH_URL` too. Rejected: a variable that changes nothing for the command and would break it when missing.

The container must run the use case inside `withPool`, so the pool closes when the command ends, also on failure.

### D5. The command and its arguments

`src/cli/commands/create-account.ts` exports `runCreateAccount`. The usage becomes `pnpm ingest account <email> [name]`. `runCli` today rejects any argument after the command name, so it passes the rest to the command and each command declares how many it takes: the existing four take none and keep their usage error (exit 2). The command reads the password only after the arguments are valid and the variables are present, so a wrong call never waits at a prompt. Output: `Created account <email>` and nothing else on success; one line per error, run through `redactSecrets`.

A password in a third position is a usage error, not a convenience: it would end in the shell history, and the spec scenario "Password in an argument is not read" tests that it is neither stored nor printed.

## Risks / Trade-offs

- [The prompt without echo depends on raw mode of the terminal and behaves differently on Windows] → written with Node's `readline` and `process.stdin.setRawMode` only when `isTTY`; checked by hand on Windows (task 5.2) because a pseudo-terminal test is not worth the cost for a one-person command.
- [`runCli` changes for every command] → the four existing commands keep their tests; a new test shows that an extra argument is still rejected for them.
- [The adapter depends on the library message `[body.email]` to name the field] → already covered by its tests in MF-20.1; a library upgrade is caught there.
- [Integration tests skipped in CI] → known deviation until MF-44; they run locally against the Neon development branch.
