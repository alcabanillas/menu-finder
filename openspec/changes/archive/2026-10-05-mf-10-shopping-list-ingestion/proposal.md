# Proposal

## Why

The shopping list leg is the only one of the three (menu, recipes, list) still parsed by a script outside the hexagon: `scripts/datos/parse-lista-compra.js`. It has no tests, reads `Lista_de_la_compra.pdf.txt` files made by hand from the PDF, and its contract is still "pending" in T2 §3. MF-11 and MF-38 already moved menus and recipes into `pnpm ingest`; this change (roadmap **MF-10**) does the same for the list, with TDD (PROC-tdd), and goes one step further: it reads the PDF directly and saves to the database, with no JSON and no TXT in between (ING-lista-compra: the list is "persisted in a relational database"; the checklist of MF-24 works against it).

Two facts measured on the 36 real PDFs shape the work. **17 of them have two pages** (menus 4, 5, 6, 11, 15, 16, 17, 20, 22, 23, 26, 30, 31, 32, 34, 35, 36) and a category can start on page 1 and continue on page 2, which a copy-paste to TXT can hide. And the page has two fixed columns, so a column that overflows continues at the top of the same column on page 2; the parser has to follow each column across the pages, as the column splitting of the old script did for the TXT.

## What Changes

- Add the shopping list entity (`ShoppingList`, `ShoppingItem`) to `src/domain/shopping/`: one list per menu, items with category, name, quantity, unit and optional flag.
- Add the PDF page parser for the list in `src/infrastructure/local-documents/pdf/` (pure function over positioned text: categories, `- name: amount` items, `(opcional)`, names wrapped on two lines, the two free-text categories, footer cut by position, pages joined).
- Extend the `DocumentSource` port with `readShoppingList` (implemented by `LocalDocumentSource` with `pdfjs-dist`, as the recipes are). The read returns the number of pages, so the report answers "which lists have two pages" for good.
- Add the `ShoppingListRepository` port and its Postgres adapter, a new `shopping_item` table (migration `004`) and the `ingestShoppingLists` use case.
- Add the CLI command `pnpm ingest shopping-list` (summary, QA report in `data/qa/`, exit code). It runs after `menu` because every item points to its menu row.
- Remove `scripts/datos/parse-lista-compra.js` and `pnpm datos:lista`, and write T2 §3.
- **Decision (confirmed by the author):** the two free-text categories, `Especias` and `Grasas y aceites`, become items with no quantity and no unit, so `ShoppingItem` has a single shape. `design.md` justifies it.
- **Deviation from the roadmap wording:** MF-10 said "revisar y documentar" and estimated ~2.5 h; the author chose to deliver the migrated, database-backed parser in one change, in phases (more than the 2 h threshold of AGENTS.md "Tamaño antes de propose"). The roadmap line is rewritten when archiving.

Out of scope: ingredient name normalization and food groups (MF-16), the per-user checked state `UserShoppingItem` and the checklist UI (MF-24), the cross-check recipes ⊆ list (open item of `context/decisiones.md` §2), any LLM.

## Capabilities

### New Capabilities
- `shopping-list-ingestion`: reads every `Lista_de_la_compra.pdf` under `data/raw/Dieta/Menu <n>/` (one or more pages) into structured items, saves them per menu in the database, and reports pages, errors and anomalies.

### Modified Capabilities
_None._ `menu-ingestion` and `recipe-ingestion` keep their requirements; the CLI gains a command and still rejects unknown ones.

## Impact

- **Code:** new `src/domain/shopping/`, `src/application/ports/shopping-list-repository.ts`, `src/application/use-cases/ingest-shopping-lists.ts`, `src/application/dto/ingest-shopping-lists.ts`, `src/infrastructure/local-documents/pdf/shopping-list-page.ts`, `src/infrastructure/postgres/postgres-shopping-list-repository.ts`, `src/cli/commands/ingest-shopping-list.ts`, `postgres/migrations/004-shopping-list.sql`. Modified: `DocumentSource` and `LocalDocumentSource` (`readShoppingList`, shared positioned-text reader), `run-cli.ts`, `cli/index.ts`, `cli-container.ts`. Removes `scripts/datos/parse-lista-compra.js` and the `datos:lista` script.
- **Data:** reads the list PDFs in `data/raw/Dieta/`; writes `shopping_item` rows and `data/qa/qa-lista-compra.md` (gitignored). No JSON dataset is produced. SEG-datos-nutricionista: the page footer (generator line, slogan) is cut by position, so the pattern file `data/marca.json` is no longer needed by this leg; a spec scenario and its test guard it. Fixtures use fictitious names generated by script.
- **Security (safety-first P1, SEG-owasp):** a local command run by the author (ING-cli-local), with no request surface. Abuses considered: A03 injection through item names → values go to Postgres as one JSON parameter, never concatenated; A08/A06 crafted or corrupt PDF through `pdfjs-dist` → the library error is caught and reported per menu, the run continues; A01 QA path escaping `data/` → rejected before writing, as in `ingest recipes`; A02 nutritionist data in the database or the output → footer never enters an item or an anomaly text; the new table has row-level security and no policy, like the others (`context/safety-first.md` §2.4).
- **Decisions relied on:** ING-lista-compra, ING-lista-dato-primario, ING-cli-local, ING-determinista, ARQ-modelo-datos, ARQ-hexagonal (ADR-001), SEG-datos-nutricionista, PROC-tdd. **Contradictions to flag:** ARQ-modelo-datos writes `ShoppingItem(menuId, category, name, qty, unit)`; this change adds `optional` and `position` (the same ingredient appears once normal and once optional, and the order of the PDF is kept) and uses `menu_number`, the natural key the other tables use. ING-trazabilidad still lists the list among documents that "pass through TXT"; this change removes the TXT step for it, so that decision is updated.
- **Docs:** `context/tareas/T2-esquema-json-ingesta.md` §3, `context/tareas/T0-extraccion-previa.md` (command), `context/decisiones.md` (ING-lista-compra, ING-trazabilidad, ARQ-modelo-datos), `context/roadmap.md` (MF-10).
- **Dependencies:** none new.
